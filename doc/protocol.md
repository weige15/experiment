# M1 protocol (locked before model inference)

## Question and scope
Do requests differ materially in their sensitivity to weight quantization of different Llama 3.1 8B layers? M1 only: measurements and a bounded research conclusion, not a router, clustering, batching, speed or memory benchmark.

## Fixed design
- Official **base** `meta-llama/Llama-3.1-8B`, revision `d04e592bb4f6aa9cfee91e2e20afa771667e1d4b`. Do not substitute Instruct or third-party quantized weights.
- BF16 weights/reference, BF16 linear activations and KV cache, PyTorch SDPA, deterministic greedy single-request decoding, seed **20261015**. The base tokenizer has **no official chat template**. Use an explicitly saved plain-text Q/A few-shot template via `apply_chat_template`, identical for every precision configuration. Three train-only examples per dataset, never evaluation examples.
- W4: deterministic round-to-nearest, symmetric per-output-channel blocks of 128 contiguous input weights; FP32 absmax/7 scale, signed integer codes clipped to [-7,7], ties-to-even rounding, no clipping optimization, no activation calibration. Quantize all seven attention/MLP linear weights per selected layer, not norms, embeddings or LM head. Real integer quantization followed by dequantization to BF16 for forward computation (Q/DQ); this isolates weight precision and does **not** benchmark packed-integer runtime performance.
- 32 layers in 8 contiguous groups of 4, zero-indexed: g0=0–3, ..., g7=28–31. Exactly one group W4 and seven BF16 in each intervention. Every group has the same weight count / conceptual precision budget.
- Data revisions: GSM8K `openai/gsm8k@740312add88f781978c0658806c59bc2815b9866`, ARC-Challenge `allenai/ai2_arc@210d026faf9955653af8916fad021475a3f00453`, BoolQ `google/boolq@35b264d03638db9f4ce671b711558bf7ff0f80d5`.
- Sample without replacement with the fixed seed. Train: 3 demonstrations + 8 separate calibration requests/dataset. Test (BoolQ validation): 8 smoke requests then **32 disjoint formal evaluation requests/dataset**. Save IDs, text, source and role. Calibration selects a fixed group, not quantizer parameters. Exclude normalized question duplicates across roles; record any exclusion. No evaluation-label tuning.
- Two predefined prompt wordings on every formal request; same content, answer format and demonstrations. Wording A: “Solve the following problem.” / “Choose the correct option.” / “Answer the question using the passage.” Wording B: “Work out the answer to this problem.” / “Select the best answer.” / “Based on the passage, respond to the question.”
- GSM8K: greedy reasoning followed by `#### <number>`, at most 256 new tokens. ARC: option label only, at most 16 tokens. BoolQ: yes/no only, at most 16 tokens. End on EOS or next-question delimiter; retain full raw output and flag truncation / parse failure. Limits are fixed, not adjusted after viewing evaluation labels.

## Measurements and validity gates
1. First run one real BF16 baseline; assert 32 layers, BF16 parameters, BF16 KV cache, tokenizer/model identity, finite outputs. Persist hardware, versions, revision, prompt, token IDs, answer, correctness, elapsed time.
2. Unit-test quantizer with analytic tensors; run one group on the same real request; prove only intended weights changed, and exact BF16 restoration. Check reference-vs-reference KL = 0 within numerical tolerance.
3. Measure one request, then all 8 groups. KL is **KL(p_BF16 || p_W4)** over the full vocabulary in FP32 at every position of the **same BF16-generated continuation** (teacher forcing with identical context). Do not compare distributions on divergent generated histories. Retain each token KL; mean full-continuation KL is primary sensitivity. Separately generate each W4 configuration's actual answer.
4. Smoke 8/dataset before formal evaluation; inspect answers, parsing, truncation, finite/nonnegative KL, complete rectangular request × group coverage, and exact restoration. Save failures; stop to fix methodological problems before scaling.
5. Rank all 8 groups per request, greatest mean KL = rank 1. Ties get average ranks; report near-ties rather than forcing an effect.

## Analysis fixed in advance
- Analyze all 96 formal source requests, separately by wording and dataset. Wording pairs are **not independent samples**. Report high-sensitivity group counts, full heatmap, rank correlation, and every request's answers / correctness.
- Pairwise reversal: for each of 28 group pairs report the number of requests preferring each direction, stratified by dataset. Near-tie if difference <= max(1e-5 nats/token, 1% of pair mean); disclose these. Report reversals that replicate in both wordings. Also analyze first/second halves of BF16 continuation; do not count one-token continuations as having two independent segments.
- Materiality: report absolute KL, normalized layer profiles, same-budget oracle regret in nats/token and correctness percentage points, not only a p-value. A heatmap or tiny nonzero differences alone is not evidence of the hypothesis.
- Wording stability: per-source Spearman rank correlation, high/low-group agreement and cross-wording selection regret. Segment stability: first-half vs second-half ranking for continuations with >=4 tokens, explicitly report denominator and missing short answers.
- Control dataset and request length: fit each group profile with dataset intercepts and log input length (also log continuation length as a sensitivity control). Report residual request×group heterogeneity and cross-wording residual association; use within-dataset length-stratified permutation of wording-B request identities to assess whether matching requests retain information beyond these controls. Avoid claiming that a residual norm alone proves causality.
- Same precision budget: compare a single fixed group selected by **calibration mean KL**, best fixed group on evaluation (**oracle**), per-request BF16-KL-minimizing group (**oracle upper bound on the KL objective**), and label-correctness-maximizing group (**label oracle upper bound**). Evaluate actual answers of every selected configuration. The KL oracle is not guaranteed to improve correctness. Cross-wording selection is an oracle diagnostic, not a deployable router.
- Bootstrap 95% percentile confidence intervals, 2,000 replicates, seed fixed; resample source requests within dataset, keeping both wordings and all groups together. Recompute evaluation-selected fixed/oracle choices within resamples. Paired CIs for improvements; report dataset CIs as well as macro-overall results.
- Include all failures, no-difference / near-tie cases, losses under oracle-KL selection, and limitations. No cherry-picked successful cases. No deployed-router claims.
- If W4 evidence is insufficient, first diagnose alignment, extraction, numerical precision and confounds; then pre-record any finer-group / W3 / longer-context exploratory protocol. Preserve all W4 results. Do not declare success by rewriting the conclusion.

BF16 → one-group W4 → single-request KL → eight-group scan → 8/dataset smoke → 32/dataset formal evaluation → analysis and audit.

Required final evidence: reproducible install with dependency lock, one-command M1 entrypoint, executed unit/smoke tests, per-request CSV including token KL and rankings, actual answers and accuracy comparison, sensitivity heatmap, `results/m1/report.md`, hardware/model/quantizer/seed/arguments metadata, full-set statistics and bootstrap CIs, explicit requirement-to-artifact completion audit.
